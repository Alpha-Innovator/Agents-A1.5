Architecture Decision Dossier: Open-Source Analytics Platform for Marketplace, Merchants, and Research

Evidence cutoff: 2026-09-16. Nature: Design investigation, not deployment or benchmark. Workload numbers are requirements to test, not measured capabilities.

1. Executive Summary

Twelve candidate systems were assessed. Seven are unsuitable as the serving layer for this platform's interactive workloads (Trino is federated query-only; DuckDB is embedded; PostgreSQL is row-store OLTP; Spark/Flink are compute/transformation engines; Materialize carries a BSL 1.1 license that prohibits unlicensed commercial production use Materialize LICENSE). Two have hard disqualifiers for specific workloads: Druid cannot do primary-key-based updates (fails Workload B) Druid update docs; Pinot lacks any open-source Iceberg integration (fails Workload C) Pinot docs.

Four candidates survive as viable serving layers: ClickHouse, Apache Doris, StarRocks, RisingWave. The recommended design uses Apache Doris as the single serving layer because it natively satisfies Workloads A–E while requiring only two counted stateful components (Debezium + Doris), and its full Iceberg engine (including V3 deletion vectors) matches the existing Spark-written lake. The materially different alternative is RisingWave, which minimizes component count to one by using its embedded Debezium CDC, at the cost of no native row-level security and less battle-tested multi-tenant isolation.

No design achieves every numerical target without measurement. The p95 <2s / 250-concurrent-users target (Workload A) and the 15-second visibility target require PoC validation; nothing in this dossier claims either is achieved.

2. Candidate Dossiers (Compact)

2.1 ClickHouse (serving OLAP)

  • License: Apache 2.0 (LICENSE). Fully OSS.
  • Architecture/deployment: Columnar MPP with MergeTree-family storage. Replication via ReplicatedMergeTree requires ClickHouse Keeper (Raft) or legacy ZooKeeper (keeper docs). Non-replicated tables keep serving queries during Keeper outage; replicated tables go read-only (replication docs).
  • Ingestion/CDC: Three Kafka paths — bundled Kafka table engine (at-least-once), Kafka Connect Sink (OSS, exactly-once opt-in with KeeperMap, beta since Jan 2023, requires ClickHouse ≥23.3) kafka sink blog, and ClickPipes (Cloud/BYOC only). For Workload B, the documented pattern is Debezium → Kafka → ReplacingMergeTree with a version column + FINAL at query time CDC blog part 1.
  • Updates/deletes/dedup: ReplacingMergeTree dedups only during background merges; reads need FINAL (which disables PREWHERE) replacingmergetree docs. VersionedCollapsingMergeTree allows out-of-order insertion with version-based collapsing vcmm docs. Lightweight deletes (GA 23.3) mark rows via hidden _row_exists column; physical removal happens at merge time, non-deterministic lightweight delete docs. Mass ALTER TABLE...DELETE|UPDATE (mutations) are async per-part, cannot roll back, and reads may see inconsistent views mid-mutation mutations docs. Dedup tokens (insert_deduplication_token) retained up to replicated_deduplication_window (default 10,000 blocks) AND replicated_deduplication_window_seconds (default 3,600s) dedup settings.
  • Joins: All SQL join types; GLOBAL JOIN broadcasts right table across shards; distributed joins over non-co-located data broadcast the right side to every shard — expensive join docs. Dictionaries recommended for LEFT dimension lookups dictionary docs.
  • Lake interop: Read+write Iceberg engine on S3/Azure/HDFS/local with type limitations; reads position and equality deletes but NOT V3 deletion vectors iceberg engine docs.
  • Isolation: RBAC + row policies (per-user row filters on tables) + quotas with tenant-keyed buckets + settings profiles + per-user memory limits. No formal workload groups access rights, quotas. Multi-tenant patterns documented: shared table with tenant_id + row policies is recommended multitenancy guide.
  • Recovery: Keeper quorum loss → read-only mode; recovery via rcvr or --force-recovery [keeper docs]. Data HA via replica sync from peers.
  • Version caveats: Lightweight deletes GA 23.3; lightweight UPDATE beta 25.8 (introduced 25.7); refreshable MVs production-ready 24.10; JSON type experimental 24.8; GROUPS frame/window changes in 2026 2023 changelog, 2024 changelog, 2025 changelog, 2026 changelog.
  • Assessment: Strongest for pure append-heavy time-series analytics (Workload A). Weakest for Workload B: correctness requires FINAL on every query (query-cost penalty) or eventual merge; no automatic late-event handling like sequence columns in Doris/StarRocks.

2.2 Apache Druid (serving OLAP)

  • License: Apache 2.0 (licensing).
  • Architecture: Master (Coordinator+Overlord), Query (Broker+Router), Data (Historical+MiddleManager). Dependencies: deep storage (S3/HDFS), metadata DB (MySQL/PostgreSQL/Derby), ZooKeeper for leader election/coordination architecture docs.
  • Ingestion/CDC: Kafka indexing service ingests with arbitrary old timestamps (no window restriction); offset commits atomic with segment metadata in the same DB transaction (exactly-once publish) storage docs, Imply EOS blog. Late events handled via lateMessageRejectionPeriod supervisor docs. Druid is NOT a CDC sink for relational tables — it has no PK-based upsert path.
  • Updates/deletes: Immutable segments only. Updates via time-range REPLACE OVERWRITE or compaction overshadowing; NO single-record PK updates update tutorial. Deletes via soft (mark unused) then hard kill task (irreversible) delete docs. Hard failure for Workload B.
  • Joins: Native broadcast hash-join limited to Druid datasources, memory-bound; MSQ adds sort-merge (all join types incl. FULL OUTER) but requires equality conditions native joins, MSQ. Lookups are key-value only via JDBC extension — not relational joins lookups.
  • Lake interop: None in OSS. No Iceberg connector.
  • Isolation: Datasource-per-tenant or shared datasource with tenant_id; query priority flags; query laning (thread reservation); dedicated Broker pools via Router; service tiering multitenancy docs, mixed workloads, router docs. No per-tenant CPU/memory quota — isolation is architectural, not governed.
  • Recovery: Deep storage is the durability boundary — single copies; if deep storage files disappear, data is permanently lost; restore = metadata import (5 tables via export-metadata tool) + deep storage file preservation deep storage docs, export-metadata docs. Segment replication factor applies only to Historical-tier copies (default 2) rule config. Metadata loss is irrecoverable — HA only mitigation metadata docs.
  • Version caveats: MSQ became core in 35.0.0 (was extension in 24.0) upgrade notes; ZK-based segment loading removed in 30.x; K8s extension enables ZK-free mode (experimental) k8s ext.
  • Assessment: Excellent pure time-series serving, but fails Workload B (no PK updates) and Workload C (no Iceberg). Also requires ZooKeeper, consuming 1 of 3 component slots.

2.3 Apache Pinot (serving OLAP)

  • License: Apache 2.0 (LICENSE).
  • Architecture: Controller, Broker, Server, Minion. Real-time tables: controller assigns servers as direct Kafka consumers; segments accumulate in memory, immediately queryable, flushed to disk architecture docs. Requires ZooKeeper for cluster state running in production.
  • Ingestion/CDC: CDC playbook with Debezium ExtractNewRecordState + delete.handling.mode=rewrite mapping to deleteRecordColumn; upsertConfig modes FULL/PARTIAL; comparisonColumns resolve out-of-order events; OutOfOrderRecordColumn/dropOutOfOrderRecord configs CDC playbook, upsert docs.
  • Updates/deletes: Primary index on REALTIME tables; partial upsert REALTIME-only; commit-time compaction at flush; soft deletes tracked via queryableDocIds/validDocIds bitmaps; deletedKeysTTL for retention metadata; UpsertCompactionTask physically rewrites segments deletes doc, compaction docs.
  • Joins: Dimension tables replicated to every server in a tenant (in-memory hash lookup by PK; cluster max 200MB) dim table docs. Colocated joins require identical partitioning colocated join docs.
  • Lake interop: None in OSS — Iceberg integration is a StarTree commercial feature Pinot docs. Hard failure for Workload C.
  • Isolation: Tenants as server/broker instance tags; workload budgets (CPU ns + memory bytes, 1.4.0+) with propagation and enforcement at admission; per-table QPS quotas (429 when exceeded); broker-level RLS filters tenants, workload isolation, quotas, RLS.
  • Recovery: ZooKeeper holds all cluster metadata; restore = ZK snapshot + restart controllers; servers re-download segments from deep store production guide.
  • Version caveats: 1.3.0 had a known multi-stream Kafka ingestion bug (not production-ready) upgrade notes; 1.4.0 changed HEAP→MMAP default and added workload budgets.
  • Assessment: Strong upsert/real-time serving, but no OSS Iceberg — fails Workload C. Requires ZooKeeper (1 of 3 slots).

2.4 Apache Doris (serving + transformation)

  • License: Apache 2.0 (LICENSE). Fully OSS, no dual license.
  • Architecture: Shared-nothing MPP: FE (metadata, planning) + BE (storage, execution). FE uses BDB JE, does NOT depend on ZooKeeper — internal Paxos-like consensus among Master/Follower/Observer roles system architecture. Default 3 replicas per tablet on BEs.
  • Ingestion/CDC: Routine Load (FE-managed Kafka consumer); Flink CDC connector with exactly-once via Stream Load 2PC; Doris Kafka Connector (sink for Avro/Protobuf/Debezium) kafka cdc docs. Exactly-once via edit-log persistence + commit-time verification routine load best practices. Auto-recovery on transient failures; terminal CANCELLED if database/table dropped routine load manual.
  • Updates/deletes: Unique Key model = Merge-on-Write since v2.1: duplicates resolved at write time via delete bitmaps, zero merge delay at query time unique key docs. function_column.sequence_col resolves out-of-order/late CDC events (larger value wins, ties fall back to load order) [same source]. __DORIS_DELETE_SIGN__ hidden tinyint for soft deletes on any load path [same source]. Partial column updates require MoW. Primary keys cannot be rewritten — use soft-delete + insert.
  • Joins: Broadcast, Shuffle, Bucket Shuffle, Colocate Join across internal tables MPP docs. Federated joins with Iceberg run as one MPP plan iceberg docs.
  • Lake interop: Full Iceberg engine: 7 catalog backends (REST recommended; Glue/DLF read-only), reads V1–V3, writes V2 default, V3 deletion vectors (Puffin) since 4.1+, DML (INSERT/UPDATE/DELETE/MERGE INTO) requires format-version ≥2, time travel, branches/tags, row lineage (experimental) iceberg docs, V3 blog. Hudi read-only; Delta Lake experimental/read-only since 3.0.1.
  • Isolation: Resource Groups (physical placement via BE tags — replicas allocated per tag, users bound to tags) resource group docs. Workload Groups (in-process CPU via cgroups, memory, IO, concurrency isolation per query group) workload group docs.
  • Recovery: FE HA via Paxos-like election; 3-replica quorum writes; automatic replica rebuild [system architecture]. RECOVER restores deleted databases/tables/partitions from recycle bin (default 1-day retention, configurable) RECOVER docs. RESTORE brings back backup snapshots with metadata AND data restore docs. No per-table rollback; erasure via __DORIS_DELETE_SIGN__ or DELETE FROM.
  • Version caveats: Iceberg V3/deletion vectors require 4.1+ with MERGE INTO/Row Lineage EXPERIMENTAL [V3 blog]; Iceberg DML requires format-version ≥2; Hudi dependent version 0.15, read-only; Delta Lake read-only experimental.
  • Assessment: Best all-around fit: native CDC semantics (sequence_col for late events, MoW for dedup), full Iceberg engine matching the existing Spark lake, built-in multi-tenant isolation, no external ZooKeeper.

2.5 StarRocks (serving + transformation)

  • License: Apache 2.0 (LICENSE). Fully OSS; commercial offerings are managed services only vendor page.
  • Architecture: Shared-nothing MPP with vectorized engine. FE: metadata (BDB JE) + Raft-based leader election among leader/follower/observer roles meta recovery docs. No external ZooKeeper required.
  • Ingestion/CDC: StarRocks Kafka Connector (sink, at-least-once; Debezium requires transforms: AddOpFieldForDebeziumRecord + ExtractNewRecordState with drop.tombstones=true) since v1.0.1 (Nov 2023) kafka connector docs. Routine Load for CSV/JSON/AVRO. Flink CDC supported.
  • Updates/deletes: Primary Key table with Delete+Insert strategy via DelVector — updates mark old row deleted in DelVector + write new row; queries read only latest version (3–10x faster than Unique Key MoR) PK table docs. merge_condition (non-PK column condition, update only if incoming ≥ existing) introduced v2.5, resolves data disorder; partial+conditional incompatible before v3.1.3 PK load docs. Primary key values cannot change.
  • Joins: Shared-nothing MPP joins architecture docs.
  • Lake interop: Iceberg external catalog since v2.4: READ + INSERT INTO from v3.1; Parquet V2 position deletes from v3.1, equality deletes from v3.1.10/v3.2.5/v3.3+; ORC V2 position deletes from v3.0, equality from v3.1.8/v3.2.3/v3.3+; Time Travel from v3.4.0 Iceberg catalog docs. Iceberg V3 deletion vectors NOT supported (open issue #63819); UPDATE on Iceberg V2 tables NOT supported (issue #72046). Default metadata cache tolerates minute-level inconsistency; iceberg_meta_cache_ttl_sec=0 forces immediate freshness feature support.
  • Isolation: Resource Groups with CPU weights (soft) or exclusive cores/percent (hard isolation since v3.3.5), memory via mem_limit, concurrency limits, classifiers by user/role/db/source_ip resource group docs. BE Labels for data placement BE label docs.
  • Recovery: Leader election among Followers; observers extend read concurrency [meta recovery docs]. No recycle-bin equivalent to Doris RECOVER. Metadata recovery last-resort: bdbje_reset_election_group=true forces node with largest lastVLSN [meta recovery docs].
  • Version caveats: Do NOT downgrade v3.3→v3.2.0–3.2.2 (metadata loss); v4.0→v3.5.0 incompatible release 3.3 notes. Iceberg V3 DV unsupported; V2 UPDATE unsupported — both open issues as of cutoff.
  • Assessment: Comparable to Doris for CDC workloads (DelVector + merge_condition). Weaker Iceberg support than Doris (no V3, no UPDATE on V2). More volatile upgrade history.

2.6 Trino (federated query engine — NOT serving)

  • License: Apache 2.0 (legal).
  • Architecture: Stateless coordinator + stateless workers; no storage of its own; data stays in external sources via connectors overview, data lake docs.
  • Role: Explicitly OLAP query engine, "not designed for point reads and updates of single rows" vision. Has Kafka/Iceberg/JDBC connectors but performs NO streaming ingestion Kafka connector. Must sit ABOVE a serving layer, not replace one.
  • Lake interop: Excellent Iceberg DML (v2 row-level deletes; v3 experimental, no row-level DML) Iceberg connector. Commit conflicts between OPTIMIZE and concurrent CDC position deletes documented (issue #25584).
  • Isolation: Resource groups with hierarchical structure, soft/hard memory limits, concurrency limits, scheduling policies (fair/weighted/query_priority) resource groups. Memory governance: per-node cap 30% heap, cluster-wide 20GB default resource management.
  • Recovery: Stateless between queries; fault-tolerant execution buffers intermediates in external storage (e.g., S3) — suited for large batch, not high-volume short queries query resiliency.
  • Assessment: Ineligible as serving layer. Can serve as the federation/joins layer over Doris+Iceberg for ad-hoc research (Workload C), but is stateless and does not hold durable state.

2.7 DuckDB (embedded OLAP — NOT serving)

  • License: MIT, fully OSS, no enterprise tier FAQ.
  • Architecture: Single-process embedded library; no server component why DuckDB.
  • Ingestion: Reads Parquet/CSV/JSON/Arrow directly; ODBC/JDBC clients; no streaming Python ingestion, Java overview.
  • Updates/deletes: DELETE exists but space reclaimed only on CHECKPOINT delete docs. Append-first design.
  • Isolation: NONE natively — no users, RBAC, or RLS security overview. Isolation must be built at application layer (e.g., separate .duckdb files per tenant).
  • Recovery: File-based WAL replay on restart crashes docs. Storage formats changed across versions (v0.8 → v1.x); backward compatible since 0.10; forward compat best-effort storage docs.
  • Assessment: Ineligible as shared serving layer. Fits as embedded analytics inside an application (e.g., merchant self-service exports), where isolation/recovery are supplied externally.

2.8 PostgreSQL (operational/OLTP source — NOT dashboard serving for A)

  • License: PostgreSQL License (BSD/MIT-like) license.
  • Architecture: Process-based row-store RDBMS with MVCC, WAL-based durability architecture.
  • CDC: pgoutput plugin (built-in, PG10+) streams WAL via replication slots; Debezium consumes it; LSN offsets; replication slots retain WAL during outages Debezium PG docs, logical replication docs.
  • Isolation: Row-Level Security policies with USING/WITH CHECK expressions per role RLS docs.
  • Performance: Row-store causes I/O amplification; analytical scans evict OLTP pages from shared buffers; vacuum contention. Consensus: PostgreSQL should be the operational SOURCE fed by CDC to a dedicated OLAP engine; vanilla Postgres ceiling falls short of p95<2s at 250 concurrent users for clickstream-scale analytics Tinybird blog, ClickHouse OLTP vs OLAP, Tinybird SaaS choices.
  • Assessment: Correct as the source of truth for orders/merchants (Workload B source). Unsuitable as the dashboard-serving layer for Workload A.

2.9 Apache Spark (compute/transformation — NOT serving)

  • License: Apache 2.0 Wikipedia.
  • Architecture: Distributed compute on RDDs/DAGs; requires external storage [Wikipedia].
  • Role: Transformation engine. Structured Streaming: checkpoints + WAL record offsets; exactly-once requires replayable sources AND idempotent sinks streaming guide. Kafka sink is at-least-once Kafka integration. Writes require explicit sink — cannot serve dashboards directly community post.
  • Lake: Spark was NOT the author of Iceberg (Netflix authored it; donated 2018/graduated 2020) Iceberg Wikipedia — but is its primary engine. Your existing 500TB lake is Spark-written.
  • Assessment: Correct as the transformation engine that maintains the Iceberg lake (Workload C writer). Not a serving option. Counts as ephemeral batch (not stateful under the accounting rule when used for batch jobs).

2.10 Apache Flink (stream processing — NOT serving)

  • License: Apache 2.0 downloads. Current stable: 2.3.0 (2026-06-25).
  • Architecture: Distributed stream processor with keyed/operator state backends (HashMap/RocksDB/ForSt) stateful processing, state backends.
  • Ingestion/CDC: Native Flink CDC sources (postgres-cdc, mysql-cdc, etc.) with exactly-once for most connectors, no Kafka intermediary needed Flink CDC overview. Debezium format support: UPDATE_BEFORE/AFTER encoded as DELETE/INSERT; table.exec.source.cdc-events-duplicate=true + PRIMARY KEY generates stateful dedup operator Debezium format docs.
  • Recovery: Checkpoints = consistent snapshots of state + input positions (Chandy-Lamport barrier alignment); savepoints = manual full snapshots. On failure, resume from last checkpoint, restoring state and rolling back to correct input position checkpointing docs, fault tolerance. End-to-end exactly-once requires replayable sources + 2PC/idempotent sinks end-to-end EOS blog.
  • Lake: Native Iceberg integration with time travel via snapshot-id/as-of-timestamp options; streaming starting strategies; TableMaintenance API for compaction/snapshot expiration/orphan cleanup inside Flink jobs Flink maintenance, Flink Iceberg config.
  • Version caveats: Flink 2.0 breaks state compatibility with 1.x 2.0 announcement; 2.3.0 changes SinkUpsertMaterializer behavior (fails at planning time when upsert key ≠ primary key unless ON CONFLICT clause) 2.3.0 announcement.
  • Assessment: Correct as the stream-transformation engine (optional, if complex stream processing beyond the serving engine's capabilities is needed). Stateful — counts as a component if deployed as a persistent streaming job.

2.12 RisingWave (streaming database — serving capable)

  • License: Apache 2.0 GitHub, blog.
  • Architecture: Cloud-native: Serving Node (stateless frontend), Streaming Node (stateful, executes stream graph, maintains state), Meta Node (central coordinator, manages metadata/checkpoints/recovery), Compactor Node (optional, LSM compaction) architecture docs. State persisted in Hummock LSM tree on object storage via OpenDAL LSM blog.
  • Ingestion/CDC: Native CDC: embedded Debezium for PostgreSQL/MySQL/SQL Server/MongoDB reading WAL/binlog directly — no Kafka intermediary needed CDC docs. Also Kafka sources with FORMAT DEBEZIUM: inserts/updates/deletes applied as op field; tombstones skipped; idempotent upserts handle Debezium restart replays append-only blog, tombstone blog, Debezium together blog. Cross-table CDC: single connection subscribes multiple tables; barriers paused during transactions for atomic visibility atomic CDC blog.
  • Updates/deletes: Tables (not sources) support UPDATE/DELETE; MVs incrementally update; corrections flow through underlying table DML or CDC changelog deletes/updates docs. Watermarks: WATERMARK FOR col AS col - INTERVAL 'N seconds' for event-time windows; late data dropped by default from windows, configurable tolerance or side-stream routing watermark blog.
  • Joins: Regular JOIN recomputes on dimension updates; process-time temporal joins (FOR SYSTEM_TIME AS OF PROCTIME()) lock in historical dimension values joins docs.
  • Consistency: Chandy-Lamport checkpoints every ~1 second (default barrier_interval_ms=1000) to object storage; read queries always fetch from last checkpoint — strongly consistent reads fault tolerance docs, data persistence.
  • Isolation: Database-level isolation (independent checkpoints, localized error recovery); resource groups (named pools of Compute Nodes, databases pinned via CREATE DATABASE ... WITH RESOURCE_GROUP); RBAC at DB/schema/table/source/MV level; RLS NOT native — workaround via logical views + GRANT/REVOKE workload isolation, access control, RLS.
  • Lake interop: Native Iceberg: internally managed tables (ENGINE = iceberg with hosted catalog) and externally managed (SOURCE/SINK with connector); REST catalog, Glue, JDBC, Hive, Lakekeeper, S3 Tables supported; time travel via FOR SYSTEM_TIME AS OF/FOR SYSTEM_VERSION AS OF; equality + position deletes applied on read of mutable tables; upsert sinks with primary_key; exactly-once sinks default; compaction and snapshot expiration via VACUUM Iceberg overview, feature support, catalogs.
  • Recovery: All stateful operators fetch states from last checkpoint; only post-checkpoint state lost (~1s at default). Recovery speed depends on loading checkpoint state from Hummock fault tolerance docs.
  • Component count: Meta Node (stateful) + Streaming/Compute Nodes (stateful) + optional Compactor = up to 3, but these form ONE deployed unit. Meta store can be existing PostgreSQL/MySQL/SQLite architecture docs.
  • Performance claims: Benchmarks cite 4.96ms avg point-select latency, 25,814 QPS — but these are vendor benchmarks, not verified for this workload serving page.
  • Version caveats: Current stable v3.0.3 (2026-08-17); v3.0.0 (2026-06-11) enabled DataFusion for batch by default and deprecated Maxwell/Canal/Citus CDC sources release notes.
  • Assessment: Strongest CDC semantics (transactional atomicity across tables, sub-second checkpoints), excellent for Workload B; good for A; Iceberg integration mature (internal + external); missing native RLS (Workload D gap). Component count can be as low as 1.

4. Workload-by-Workload Analysis and Architecture Choices

4.1 Workload A — Append-only clickstream (3 TB/day, 30-day hot, late ≤72h, dashboards by product/campaign/minute, <15s visibility, p95 <2s @ 250 users)

Plausible combinations:

  1. ClickHouse Kafka engine → ClickHouse clusters — strongest raw ingest throughput; late events absorbed into MergeTree parts; dashboards need FINAL or pre-aggregated materialized views for correctness (performance tradeoff). Dashboards by product/campaign/minute map naturally to preaggregations. 15s visibility achievable end-to-end; p95 <2s well-documented for aggregate queries. Rejected as sole engine because it cannot serve Workload B without FINAL penalties on every order query.
  2. Druid Kafka supervisor → Druid — late events absorbed into active intervals without window restrictions; sub-second dashboards native. Rejected because no PK updates (Workload B fail) and no Iceberg (Workload C fail).
  3. Pinot real-time tables → Pinot — upserts native; late events configurable. Rejected because no OSS Iceberg (Workload C fail) and requires ZooKeeper (component budget).
  4. Doris Routine Load → Doris — Kafka consumer managed by FE; detail tables + materialized views for dashboard rollups; 15s end-to-end achievable (Debezium poll ~500ms + ingest). p95 <2s plausible for aggregated queries on Doris. Selected as primary serving layer (see §5).
  5. RisingWave Kafka source → RisingWave — sub-second point queries; incremental MVs maintain dashboard rollups; watermarks handle late events. Alternative (see §5).

Conflict: 3 TB/day ≈ 35 GB/min. No measured result here validates any engine meets the p95 <2s / 250-concurrent-target; that target is a PoC acceptance criterion (§7). The 15-second visibility target is architecturally plausible on Doris/RisingWave/ClickHouse but must be measured end-to-end including Debezium batching.

4.2 Workload B — Mutable order analytics via CDC (PostgreSQL → CDC, deletes, out-of-order, connector restarts, schema changes, backfills; joins with changing dims)

What a user observes while updates apply: No serving engine provides a guaranteed atomic multi-table snapshot from CDC alone. Per-table guarantees exist; cross-table consistency depends on the sink:

  • Doris: Each Unique Key table resolves duplicates at write time (MoW + delete bitmap) [unique key docs]. Sequence_col resolves out-of-order per key. But two tables (orders + refunds) updated independently means a query at any instant may see orders at T1 and refunds at T0 — not a consistent multi-table snapshot. Joins with dimensions: if dimension table also updating, the join may mix versions. Users observe eventual per-key correctness, not transactional cross-table atomicity, unless the serving engine preserves source transaction boundaries (RisingWave does via barrier pausing [atomic CDC blog]).
  • StarRocks: Same per-key semantics via DelVector; merge_condition resolves disorder. Same multi-table caveat.
  • RisingWave: Native CDC pauses barriers during transactions; buffered events flush atomically on COMMIT — preserving cross-table transactional atomicity into tables [atomic CDC blog]. This is the ONLY candidate with documented cross-table consistency for CDC-sourced tables.
  • ClickHouse: ReplacingMergeTree FINAL gives per-table correctness eventually; no cross-table atomicity.
  • Pinot: Per-key upserts; same multi-table caveat as Doris/StarRocks.

Backfills: Any backfill re-ingests historical data. With sequence_col (Doris) or merge_condition (StarRocks), newer sequence values win regardless of ingestion order. RisingWave handles via primary-key upserts. All require the dedup logic to be correct at ingestion.

Schema changes: Debezium + Schema Registry with FULL_TRANSITIVE compatibility avoids connector stalls schema registry docs. The serving engine must accept new columns — all candidates add columns to tables without rewriting data (metadata-only). Note: Doris Unique Key tables cannot change primary keys; StarRocks PK values cannot change; RisingWave tables allow updates/deletes on non-PK columns.

Selected combination: Doris (single serving layer, all sub-workloads covered, no external coordination). RisingWave is the alternative if cross-table CDC atomicity is deemed critical (it is the only candidate with that guarantee documented).

4.3 Workload C — Existing Spark Iceberg lake (500 TB, partition/schema evolution, time travel, joins with operational data, selective access)

Catalog/file-format/delete-file/concurrent-writer assumptions:

  • The lake's catalog is whatever Spark uses (HMS, REST, or Glue). If HMS: JVM-only Thrift protocol, no credential vending, single-point risk HMS docs. If REST: vendor-neutral, OAuth2, credential vending — recommended for multi-engine REST docs.
  • Files: Parquet (most likely), V1/V2 format. Delete files: equality deletes (V1+) or position deletes (V2). Deletion vectors only if upgraded to V3 spec.
  • Concurrent writers: OCC with CAS commits; commit conflicts auto-retried; data update conflicts fail with ValidationException requiring custom retry reliability docs, AWS blog.
  • Selective access without copying: engines read Iceberg metadata directly and prune via partition/column statistics — no data movement needed.

Engine compatibility with the existing lake:

  • Doris: Full Iceberg engine — reads V1–V3, federated joins as single MPP plan, DML on V2+, V3 DV support in 4.1+ [iceberg docs]. Best match.
  • StarRocks: External catalog — reads fine; V3 DV unsupported (issue #63819); UPDATE on V2 unsupported (issue #72046). Time travel from v3.4.0+.
  • ClickHouse: Iceberg table engine — read+write with type limitations; reads position/equality deletes but not V3 DV [iceberg engine docs].
  • RisingWave: Native Iceberg — internally managed and external modes; equality/position deletes applied on read; upsert sinks; time travel; REST/Glue/JDBC/Hive catalogs [Iceberg feature support].
  • Trino: Best Iceberg DML among query engines but not a serving layer.

Selected: Doris (full engine + V3) or RisingWave (native, comprehensive). Both avoid data copying.

4.4 Workload D — Multi-tenant embedded reporting (2,000 merchants; IDs ≠ access control; cross-tenant isolation; shared service exhaustion prevention; internal analyst may compare)

Required separations:

  1. Row filtering: Doris — row policies per user/role referencing current_user/roles [access rights]. RisingWave — filtered logical views + GRANT/REVOKE (RLS not native) [RLS docs]. ClickHouse — row policies [access rights]. Pinot — broker RLS filters [multi-tenant playbook]. Druid — datasource/tenant_id with Router routing [multitenancy docs].
  2. Credentials: All serving engines have RBAC (users/roles/privileges). Doris: standard SQL GRANT/REVOKE. RisingWave: user-based privileges at DB/schema/table levels. ClickHouse: users + roles + row policies.
  3. Query scheduling: Doris: workload groups with max_concurrency/max_queue_size [workload group docs]. RisingWave: resource groups pin databases to node pools [workload isolation]. ClickHouse: quotas with quota_key and keyed_by_normalized_query_hash [quotas]. Pinot: bounded_fcfs scheduler + token bucket query scheduling.
  4. Memory limits: Doris: workload groups (cgroups memory) [workload group docs]. RisingWave: resource groups with mem_limit [resource group docs]. ClickHouse: per-user max_memory_usage + quotas [quotas].
  5. Workload groups: Doris (native), RisingWave (native), ClickHouse (quotas fill the role), Pinot (workload budgets 1.4.0+).
  6. Infrastructure isolation: Druid's dedicated Broker pools + watchedTiers [mixed workloads docs]; Doris Resource Groups via BE tags [resource group docs]; RisingWave resource groups [workload isolation].

Internal analyst comparing merchants: Requires a role above row-level filtering — e.g., a research role granted SELECT on the shared table without a tenant filter, or on a view aggregating across tenants. This is role-based, not tenant-based — implement via GRANT. All candidates support this via RBAC.

Tenant abuse (one tenant exhausting shared service): Mechanisms: Doris workload groups (concurrency limits), RisingWave resource groups (node pool pinning), ClickHouse quotas (per-tenant keys), Pinot workload budgets + QPS quotas (429 responses). Druid: query laning + dedicated brokers (architectural).

Selected: Doris (resource groups + workload groups + row policies, all native). RisingWave alternative lacks native RLS — a real gap for "merchant identifiers alone are not an access-control mechanism" (the requirement explicitly says IDs must not be the mechanism; filtered views still rely on the view definition being correct — operationally acceptable but weaker than engine-enforced RLS).

4.5 Workload E — Corrections and erasure (dimension correction across dashboards + historical tables; erasure covering MVs, lake snapshots, caches, backups)

Corrections (bad dimension mapping):

  • Hot dashboards: Corrections must propagate to serving-layer tables. Doris: UPDATE/DELETE on fact tables triggers MoW rewrite; materialized views refresh automatically [unique key docs]. RisingWave: table DML propagates to dependent MVs incrementally [deletes/updates docs]. ClickHouse: mutations rewrite parts asynchronously [mutations docs].
  • Historical tables (Iceberg): Spark MERGE INTO or engine DML (Doris/Trino/Flink) rewrites data files; compaction (rewrite_data_files) absorbs pending deletes compaction docs.
  • Caches: Application-level caches must be invalidated or updated — no engine controls external caches.

Erasure (approved data-erasure request):

  • Logical delete becomes invisible when: (a) the serving engine applies the delete so queries no longer return the row (immediately for Doris MoW delete sign; after merge for ClickHouse lightweight delete); (b) the Iceberg lake applies a delete file (equality/position) so time-travel snapshots after the delete exclude it; (c) materialized results are recomputed or dropped.
  • Physical remnants that may remain: ClickHouse masked rows (_row_exists=false) persist until merge; mutations leave old parts until replacement [lightweight delete docs]. Iceberg: expired snapshots and orphaned files (data files no longer referenced) require expire_snapshots + remove_orphan_files — orphan cleanup compares path strings against metadata and needs full storage listing; older_than default 3 days must exceed longest write duration orphan cleanup, [compaction docs]. Backups: a backup taken before erasure retains the data — operator retention policy governs. Deleting from a live cluster does NOT retroactively alter immutable backup media.
  • Caches: Any CDN/BI cache holding materialized results must be invalidated externally — engines cannot reach into application caches. This is a control gap requiring operational procedure, not engine capability.

Selected: Doris for hot-layer corrections (native DML); Spark for lake corrections (Iceberg DML/compaction); external invalidation procedures for caches/backups.

4.6 Workload F — Recovery and portability (Kafka consumer outage, node loss, bad schema rollout, rebuild from durable storage; no duplicated revenue; ≤3 stateful components)

Guarantee analysis:

  • Duplicate CDC delivery: The primary duplicate source is Debezium's offset-commit gap (events published but not flushed to offset store → replayed on crash) [Kafka/Debezium research]. Defense: downstream sinks keyed on (PK + LSN) with idempotent upserts. Doris MoW dedups at write time by PK; RisingWave idempotent upserts; ClickHouse ReplacingMergeTree dedups at merge. For revenue-critical joins, dedup alone is insufficient — verify with PoC §7.
  • Out-of-order updates: Sequence columns (Doris), merge_condition (StarRocks), watermarks (RisingWave/ClickHouse), or stateful dedup (Flink). Druid rejects late messages via rejection periods.
  • Retention dependencies: Kafka log retention must exceed expected consumer downtime; offsets.retention.minutes (default 7 days) governs committed offset availability; tombstone visibility bounded by delete.retention.ms (24h default) — slow consumers miss deletes [Kafka/Debezium research].
  • What a rollback restores:
    • Doris: RECOVER restores deleted objects from recycle bin (1-day default); RESTORE restores backup snapshots with metadata AND data [restore docs]. Rollback of data changes = no per-table undo; use delete signs/soft deletes.
    • RisingWave: rollback to last checkpoint (~1s state loss); no point-in-time restore within streaming state.
    • ClickHouse: mutations irreversible once submitted (KILL MUTATION possible); data recoverable only from replicas/backups.
    • Druid: metadata export (5 tables) + deep storage files; segment-level rollbacks via version management within kill retention.
    • Iceberg lake: time travel to previous snapshots; expire_snapshots/orphan cleanup maintainable.

Rebuilding a cluster from durable storage must not silently duplicate revenue: The risk is replaying from an offset already consumed (duplicates) or from a stale position (missed events). All candidates require explicit offset management: Doris Routine Load commits to FE edit log [routine load best practices]; RisingWave manages its own consumer group offsets [Debezium together blog]; ClickHouse Kafka Connect Sink tracks offsets in KeeperMap DESIGN.md. The operator must define and test the exact recovery procedure (which offsets, which checkpoints) before production.

Selected: Doris — documented exactly-once via edit-log persistence + commit verification [routine load best practices]; explicit procedures for offset management.

Where requirements conflict:

  • 30-day hot retention on 3 TB/day = 90 TB hot data. Doris BEs must hold this — capacity planning required (to be validated). Alternatively tier warm/cold storage (Doris supports decoupled storage-compute mode).
  • Late events ≤72h: Doris sequence_col keeps newer state; older late events simply become the "newer" version and overwrite current state — semantically correct per source-of-truth ordering, not "reverted." If the business wants late events appended rather than overriding, configuration differs.
  • Multi-table consistency for Workload B: Doris does NOT provide atomic multi-table snapshots from independent CDC streams. If the business requires it, RisingWave's transactional-barrier CDC is the only candidate with that guarantee.
  • Erasure: logical deletion + background merges leave masked rows temporarily; compliance audits may require proof of physical removal — Doris mutations provide deterministic rewrite but scheduled TTL-based cleanup timing is not guaranteed.

  • PostgreSQL as dashboard serving layer for Workload A: row-store ceiling insufficient at scale per multiple sources [Tinybird blog, ClickHouse benchmark analysis]. Ineligible on performance grounds.

8. Evidence-Backed Decision Summary

Established facts (directly sourced)

  • Doris Unique Key = Merge-on-Write since v2.1, with sequence_col resolving out-of-order CDC and __DORIS_DELETE_SIGN__ for soft deletes [unique key docs].
  • RisingWave native CDC pauses barriers during transactions, preserving cross-table atomicity [atomic CDC blog]; Chandy-Lamport checkpoints every ~1s; reads served from last checkpoint [fault tolerance docs].
  • Iceberg V3 deletion vectors: Spark fully supported; Doris 4.1+ reads/writes V3; StarRocks does NOT support V3 (open issue #63819); Trino v3 row-level DML not supported (experimental) [Doris V3 blog, StarRocks feature support, Trino Iceberg connector].
  • Kafka/Debezium end-to-end exactly-once: snapshot phase never covered by EOS; offset-commit gap is the primary duplicate source; tombstone visibility bounded by delete.retention.ms [Kafka/Debezium research].
  • Doris does NOT require ZooKeeper (BDB JE + internal consensus) [system architecture]; ClickHouse requires Keeper; Druid/Pinot require ZooKeeper.
  • Materialize is BSL 1.1 (not OSS for production) [LICENSE]; Trino is federated-only; DuckDB embedded-only; Spark/Flink are compute engines.

Architectural judgments (ours, with reasoning)

  • Single serving layer over dual engines: Adds one more stateful component; the 3-component budget permits it only if ZooKeeper-requiring engines are excluded. Doris satisfies all five serving-side workloads natively.
  • Doris over StarRocks: Both handle CDC well; Doris wins on Iceberg maturity (V3 DV support, DML on V2+) and cleaner upgrade history. StarRocks' documented incompatibilities (V3 DV unsupported, V2 UPDATE unsupported, downgrade metadata loss) raise operational risk.
  • Doris over RisingWave (recommended): Doris has native row-level security (requirement D says IDs alone are not access control — engine-enforced RLS is stronger than view workarounds), a more complete Iceberg engine (V3), and RECOVER/RESTORE semantics for disaster recovery. RisingWave's advantages (transactional CDC atomicity, lower component count) are real but its RLS gap is a direct requirement violation.
  • RisingWave as alternative: Chosen when component minimization outweighs RLS needs; its native CDC also removes Debezium from the stack entirely.
  • ClickHouse ineligible as primary: While strongest for pure clickstream analytics, its CDC handling (FINAL dependency, eventual dedup) conflicts with Workload B's correctness requirements at query time. Retain as evaluation candidate only if Workload B semantics can tolerate it.

Unresolved questions (bounded)

  • Performance targets unverified: p95 <2s @ 250 concurrent users and 15-second visibility require PoC measurement with the platform's actual query shapes and data distribution.
  • 30-day hot retention capacity: 90 TB hot data on Doris BEs — storage and memory sizing not yet validated; decoupled storage-compute mode may be needed.
  • Iceberg V3 in the existing lake: Unknown whether the 500TB lake was written with V3 (deletion vectors) — Doris V3 support requires format-version 3 set at creation [V3 blog]. If the lake is V1/V2, Doris still reads it fully.

  • RisingWave Iceberg internal catalog at 500TB scale: Feature-complete per docs but untested at your lake size.
  • Multi-tenant abuse measurement: Quota/budget effectiveness depends on query characteristics — measure in PoC.
